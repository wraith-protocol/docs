When you send tokens to a brand-new stealth address on Stellar, the recipient account must be
activated with a **1 XLM minimum base reserve**. For a single payment this is a minor inconvenience.
For an airdrop to 100 recipients it becomes a coordination problem: who carries those 100 XLM, and
how is the cost tracked and recovered?

Stellar's **sponsored reserves** feature solves this cleanly. A paymaster account wraps the entire
batch in `BeginSponsoringFutureReserves` / `EndSponsoringFutureReserves` operations, taking
responsibility for each new account's reserve during account creation. The paymaster can
recoup the cost later or absorb it as an operational expense — either way, recipients need zero XLM
to start spending.

## How Stellar Sponsored Reserves Work

Every Stellar account requires a minimum XLM balance — **1 XLM base reserve** — before it can hold
any balance. Normally the sender pays this by funding the account with `createAccount`. With sponsored
reserves the paymaster pays instead:

```
BeginSponsoringFutureReserves(sponsored = recipient_address)
  └─ CreateAccount(destination = recipient_address, startingBalance = "0")
EndSponsoringFutureReserves(sponsored = recipient_address)
```

The `BeginSponsoringFutureReserves` operation designates a sponsor for any ledger entries created
between it and the matching `EndSponsoringFutureReserves`. The `CreateAccount` with
`startingBalance = "0"` activates the account while the sponsor covers the 1 XLM reserve obligation.

### Reserve vs. Fee — What the Paymaster Actually Pays

| Cost | Who pays | When refunded |
|---|---|---|
| **1 XLM base reserve** per new account | Sponsor (paymaster) | When the sponsored account is merged with `AccountMerge` |
| **Trustline reserve** (0.5 XLM per non-native asset) | Sponsor or recipient, depending on who calls `ChangeTrust` under sponsorship | Same: on trustline removal |
| **Transaction inclusion fee** | Transaction source account (or fee-bump payer) | Never — burned by network |
| **Soroban resource fee** | Transaction source account (or fee-bump payer) | Never — burned by network |

Key insight: **reserves are a loan, not a burn.** The paymaster's 100 XLM for 100 accounts is locked
on-chain but returned in full when every sponsored account is eventually merged. Fees, by contrast,
are gone permanently.

### When Sponsorship Is Refunded

A sponsor recovers its locked XLM when the sponsored account calls `AccountMerge` and designates a
merge destination. The `AccountMerge` operation transfers the account's balance to the destination
and unlinks all sponsored ledger entries, returning the reserve obligation to the sponsor's available
balance.

Recipients can do this after spending stealth funds: sweep the token balance out, then merge the
empty stealth account, returning the 1 XLM reserve to the paymaster.

## Transaction Structure for a Sponsored Batch

Keep the reserve operations in a classic transaction. Use a separate Soroban transaction
for the `stealth-sender` contract's `batch_send`, which transfers the tokens and announces each
payment. Build both from the **same** derived recipients so the activated accounts match
the announcement data. The transactions settle separately.

This testnet example builds unsigned XDR. It needs no RPC connection, funded account,
or wallet secret. The source accounts, contract ID, sequence numbers and recipient keys
in the fixture are public test inputs. Never fund the fixture addresses or use its keys
for real payments.

## Generate deterministic test recipients

```typescript
import {
  decodeStealthMetaAddress, deriveStealthKeys, encodeStealthMetaAddress,
  generateStealthAddress, SCHEME_ID,
} from "@wraith-protocol/sdk/chains/stellar";
import {
  Account, Address, Asset, BASE_FEE, Contract, Keypair, Networks, Operation,
  StrKey, TransactionBuilder, nativeToScVal, xdr,
} from "@stellar/stellar-sdk";

// Test fixture only. A real recipient derives their own keys privately and
// shares only the encoded public meta-address with the sender.
function fixtureMetaAddress(index: number): string {
  const signature = new Uint8Array(64);
  new DataView(signature.buffer).setUint32(0, index);
  const { spendingPubKey, viewingPubKey } = deriveStealthKeys(signature);
  return encodeStealthMetaAddress(spendingPubKey, viewingPubKey);
}
```

The first test recipient (index 0) is
`st:xlm:5a1922b5614eed2ef72ebad40abc5d014f7c27b6e1de5dc36976e9eec4cbe29e6b912a495f9f14513d54a00a7887f986d394a30a77239475caf211e8094b6cdb`.

## Build the sponsored batch

The fixture assumes all recipients are new accounts and sends native XLM, which
requires no trustline. For an issued asset, arrange its trustline and authorization
before sending. This example limits a chunk to 24 recipients (72 classic operations).
Size the Soroban invocation separately using simulation on the target network.

```typescript
function buildSponsoredBatch(
  metaAddresses: string[],
  sponsor: Account,
  sender: Account,
  senderContractId: string,
) {
  if (metaAddresses.length < 1 || metaAddresses.length > 24) {
    throw new RangeError("Expected a chunk of 1 to 24 recipients");
  }
  const recipients = metaAddresses.map((meta) => {
    const { spendingPubKey, viewingPubKey } = decodeStealthMetaAddress(meta);
    return generateStealthAddress(spendingPubKey, viewingPubKey);
  });

  const networkPassphrase = Networks.TESTNET;
  const options = { fee: BASE_FEE, networkPassphrase };
  const reserves = new TransactionBuilder(sponsor, options);
  for (const { stealthAddress } of recipients) {
    reserves.addOperation(Operation.beginSponsoringFutureReserves({ sponsoredId: stealthAddress }));
    reserves.addOperation(Operation.createAccount({ destination: stealthAddress, startingBalance: "0" }));
    reserves.addOperation(Operation.endSponsoringFutureReserves({ source: stealthAddress }));
  }

  const call = new Contract(senderContractId).call(
    "batch_send",
    new Address(sender.accountId()).toScVal(),
    new Address(Asset.native().contractId(networkPassphrase)).toScVal(),
    xdr.ScVal.scvU32(SCHEME_ID),
    xdr.ScVal.scvVec(recipients.map(r => new Address(r.stealthAddress).toScVal())),
    xdr.ScVal.scvVec(recipients.map(r => xdr.ScVal.scvBytes(Buffer.from(r.ephemeralPubKey)))),
    xdr.ScVal.scvVec(recipients.map(r => xdr.ScVal.scvBytes(Buffer.from([r.viewTag])))),
    xdr.ScVal.scvVec(recipients.map(() => nativeToScVal(10_000_000n, { type: "i128" }))),
  );
  return {
    recipients,
    reserves: reserves.setTimeout(120).build(),
    payment: new TransactionBuilder(sender, options).addOperation(call).setTimeout(120).build(),
  };
}
```

## Try the first chunk of 100 test recipients

## Use real recipient input

1. Supply meta-addresses from your recipients in place of `testRecipients`. Keep their
   spending and viewing keys private. Use a fresh stealth destination per payment.
2. Use the intended network, token and a verified deployment of the sender contract.
   The [registry](/reference/contract-registry) does not list a live testnet sender address.
3. Load fresh source account sequences. Only sponsor accounts confirmed absent on the
   ledger. Propagate RPC failures. Each new account must authorize its own
   `endSponsoringFutureReserves`. Give each recipient their unsigned reserve envelope and the
   matching public record from `batch.recipients` (stealth address, ephemeral public key
   and view tag). Their wallet can verify the destination and co-sign. The sender cannot
   sign for the recipient.
4. Confirm account creation before simulating and preparing the contract call with
   the real sender. Review amounts and destinations, obtain the required signatures,
   then submit. An unsigned envelope built offline does not verify network authorization
   or available reserves.

## Cost Model for 100 Recipients

For 100 newly sponsored accounts and a base reserve of 0.5 XLM, the sponsor locks
100 XLM in account reserves. Each sponsored trustline for an issued asset adds one
base reserve. Existing accounts need no creation reserve. Budget for classic inclusion
fees separately from the payment contract's simulated resource fee.
See [Stellar Fee Estimation & Budgeting](/guides/stellar-fees).

## Failure Modes

| Result | What to check |
|---|---|
| `op_low_reserve` | Check the sponsor's available balance after existing reserve obligations. |
| `tx_bad_auth` | Verify the sponsor and each newly sponsored account authorized the classic envelope. |
| `op_no_trust` | For an issued asset, confirm each account has authorized the correct trustline. |
| Failed contract call | Check the contract deployment, network, token, and simulation result before signing. |

## Recovering Sponsored Reserves

A recipient can remove an empty trustline and merge an eligible account to release its
sponsored reserves. The recipient authorizes these operations with their stealth spending
key. Keep the keys and authorization inside the recipient's wallet.

## Futurenet Testing

Futurenet runs the latest Soroban preview protocol. Wraith contracts are not deployed there, but
you can test the sponsorship and account-creation mechanics in isolation:

```typescript
import { Networks } from "@stellar/stellar-sdk";
import { rpc as SorobanRpc } from "@stellar/stellar-sdk";

const FUTURENET_RPC        = "https://rpc-futurenet.stellar.org";
const FUTURENET_PASSPHRASE = Networks.FUTURENET;   // "Test SDF Future Network ; October 2022"
const FUTURENET_FRIENDBOT  = "https://friendbot-futurenet.stellar.org";

// Fund sponsor on Futurenet
async function fundOnFuturenet(address: string): Promise<void> {
  const res = await fetch(`${FUTURENET_FRIENDBOT}?addr=${address}`);
  if (!res.ok) throw new Error(`Friendbot failed: ${res.status}`);
  console.log("Funded on Futurenet:", address);
}

// Swap these into any of the examples above to target Futurenet:
// const horizon = new Horizon.Server("https://horizon-futurenet.stellar.org"); // if available
const futurenetSoroban = new SorobanRpc.Server(FUTURENET_RPC);
void futurenetSoroban; // ready for use with FUTURENET_PASSPHRASE
```

<Warning>
  Futurenet resets without notice and runs pre-release protocol versions. Use it to
  validate sponsorship mechanics against upcoming Stellar upgrades, not for integration testing.
  For full end-to-end airdrop testing with Wraith contracts, use **testnet**.
  See [Stellar Networks](/reference/stellar-networks) for a full comparison.
</Warning>
